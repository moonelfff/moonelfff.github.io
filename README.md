# ekaterinazhuk.ru

Сайт клинического психолога Екатерины Жук. Этот файл состоит из двух частей:

- **[Для владельца сайта](#для-владельца-сайта)** - как редактировать сайт через админку, без программирования.

# Для владельца сайта

## Страницы сайта

Адрес теста состоит из `/tests/` и его «слага» (латинское название, например `what-is-your-superpower`).

## Как войти

1. Откройте https://ekaterinazhuk.ru/admin/login (удобно добавить в закладки на телефоне).
2. Введите пароль и нажмите «Войти».
3. Выйти можно кнопкой «Выйти» в верхней панели.

Админка удобна и с телефона, и с компьютера.

## Как изменить сайт: 3 шага

1. **Измените** нужное поле.
2. **Нажмите «Сохранить»** в нижней панели (на компьютере также Ctrl+S или Cmd+S).
3. **Дождитесь уведомления** «Изменения сохранены» и обновите сайт - правки сразу видны всем.

Если что-то пошло не так, нажмите **«Отменить»** - поля вернутся к последнему сохранённому состоянию. Если уйти со страницы с несохранёнными правками, сайт предупредит об этом.

### Как заменить фото

1. В блоке «Изображения» нажмите на нужное фото и выберите файл.
2. Фото **загружается и сохраняется сразу** - кнопка «Сохранить» для него не нужна.

Советы:
- **Фото профиля** - вертикальное (на сайте показывается в пропорции 4:5), минимум 1200 пикселей по длинной стороне. Превью в админке показывает его так же, как увидят посетители.
- **Картинка для ссылок (OG)** - лучше всего 1200×630. Её видно, когда ссылкой на сайт делятся в мессенджерах и соцсетях.

### Как оформить текст

Тексты пишутся в простой разметке (Markdown). Результат виден в предпросмотре рядом.

```text

- пункт списка
- ещё пункт

```

Полная [шпаргалка по Markdown](https://gist.github.com/fomvasss/8dd8cd7f88c67a4e3727f9d39224a84c).

### Как изменить тарифы

1. В блоке «Тарифы» откройте нужную услугу.
2. Измените название, цену или состав пакетов (например, «1 встреча», «4 встречи»).

## Раздел «Тесты» (`/admin/tests`)

Здесь редактируются психологические тесты, доступные на странице `/tests`:

- название и описание теста (описание поддерживает Markdown);
- вопросы и варианты ответов (один вариант, несколько, выпадающий список, текст, шкала-рейтинг), обязательность, перемешивание вариантов;
- порядок вопросов - стрелками (на компьютере ещё и перетаскиванием);
- «Как проходить тест»: по одному вопросу или списком, нумерация, перемешивание вопросов;
- «Подсчёт и толкование результатов» - без кода и JSON:
  - **Сумма баллов**: отметьте вопросы (и «обратные»), задайте минимум/максимум (можно определить автоматически) и уровни с текстом толкования; редактор предупредит о пропусках и перекрытиях диапазонов;
  - **Типы (группы)**: для каждой группы выберите вопросы и напишите толкование, укажите, какие ответы считаются «за» и сколько лидирующих групп показывать;
- служебные JSON-параметры теста и вопросов спрятаны в блоках «Дополнительно (для опытных)» - трогайте их, только если понимаете, что делаете; в случае ошибки нажмите «Отменить».

### Подсказки в админке

Рядом со сложными настройками стоит кружок **«?»**: наведите на него курсор (на телефоне - нажмите), и появится пояснение простыми словами. Подсказки есть у типа вопроса, значений вариантов, подсчёта результатов (диапазоны, группы, засчитываемые ответы), адресов (slug), цены со скидкой и других полей.

После изменений нажмите «Сохранить» и откройте тест на сайте, чтобы проверить результат.

На сайте тест оформлен карточками и кнопками в стиле сайта: описание → вопросы с прогресс-баром → результат. Если вопросов на странице больше 8, они показываются по одному с автопереходом. Два коротких демо-теста (`demo-stress-level`, `demo-communication-style`) лежат в `supabase/seed/tests.json`; если они не нужны, удалите их в админке.

# Для разработчика

Подробное описание архитектуры - в [PROJECT.md](PROJECT.md), правила для ИИ-ассистентов - в [AGENTS.md](AGENTS.md).

## Стек

Next.js (App Router, Turbopack), React, Tailwind CSS 4, SurveyJS, TypeScript. Node.js 24 LTS. Два режима хранения: Supabase (БД и Storage) для Vercel либо MySQL/MariaDB (`mysql2`) и файлы изображений на сервере для Beget.

## Запуск

```bash
npm ci
cp .env.example .env.local   # задайте ADMIN_PASSWORD и ключи Supabase
npm run seed                # однократно: загрузить начальные данные в Supabase
npm run dev                  # http://127.0.0.1:3020
npm run build && npm start   # продакшн-режим (порт 3020)
```

## Переменные окружения

| Переменная | Описание |
|---|---|
| `ADMIN_PASSWORD` | пароль админки (обязательно) |
| `ADMIN_SESSION_TOKEN` | случайная строка для сессионной cookie (рекомендуется в продакшне) |
| `DATA_PROVIDER` | `supabase` (по умолчанию) или `mysql`; переключение только явно |
| `SITE_PREVIEW` | `1` для тестового стенда: отключает аналитику и структурированные данные, задаёт `noindex, nofollow`; в рабочем окружении — `0` |
| `NEXT_PUBLIC_SUPABASE_URL` | URL проекта, обязательно в режиме Supabase и при переносе |
| `SUPABASE_SERVICE_ROLE_KEY` | серверный ключ Supabase, только для режима Supabase/переноса; никогда не публиковать |
| `SUPABASE_STORAGE_BUCKET` | бакет для изображений, по умолчанию `site-images` |
| `MYSQL_HOST`, `MYSQL_PORT` | адрес MySQL; порт по умолчанию 3306 |
| `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE` | учётная запись и база для режима MySQL, только на сервере |
| `MYSQL_SSL_CA` | путь к PEM-сертификату CA для проверяемого TLS; для удалённой БД через недоверенную сеть обязателен |
| `MEDIA_ROOT` | абсолютный путь к постоянному каталогу изображений вне `public`/`public_html`, обязательно для MySQL |
| `NEXT_PUBLIC_SURVEYJS_LICENSE_KEY` | лицензионный ключ SurveyJS (опционально) |

## Устройство админки

- `/admin/login` - вход по `ADMIN_PASSWORD`, `/admin` - контент, `/admin/tests` - тесты.
- Все правки сохраняются одной кнопкой в нижней панели (Ctrl/Cmd+S), «Отменить» возвращает последнее сохранённое состояние; при несохранённых изменениях браузер и вкладки предупреждают о потере данных. Результат показывается всплывающими уведомлениями.
- Изображения загружаются сразу после выбора файла (`/api/admin/image`: ресайз в WebP, ширина до 2400px, качество 90).
- Интерфейс mobile-first (кнопки и поля от 44px), в палитре сайта; порядок элементов меняется стрелками, на широких экранах - ещё и перетаскиванием.

## Где хранятся данные

Источник выбирает `DATA_PROVIDER`. По умолчанию остаётся **Supabase**, поэтому существующий Vercel-деплой не меняется. В режиме **MySQL** все тексты, тарифы и тесты читаются из MySQL; изображения — из `MEDIA_ROOT` через `/media/...`. Автоматического переключения на другую базу или начальные файлы нет: ошибки выбранного хранилища возвращаются явно.

- `site_content`: ключ `content_json` (общая информация, контакты) и по ключу на каждый markdown (`profile.md`, `blog.md`, `pricelist/*.md`).
- `tariffs`, `tariff_packages`: прайс (страница загружает его на сервере).
- `psychological_tests`: тесты.
- Storage-бакет (Supabase) либо `MEDIA_ROOT` (MySQL): изображения.

Каталог `supabase/seed/` содержит только начальные данные для `npm run seed` (`content.json`, `markdown/**`, `tests.json`).

### Настройка Supabase

1. Выполните в SQL Editor файлы `supabase/site_content.sql`, `supabase/tariffs.sql`, `supabase/tests.sql`.
2. Создайте **публичный** Storage-бакет (по умолчанию `site-images`).
3. Задайте `NEXT_PUBLIC_SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` в `.env.local` (и в Vercel).
4. Загрузите начальные данные: `npm run seed`. Скрипт заполняет только пустые таблицы; `npm run seed -- --force` перезаписывает данные.

### MySQL и изображения на сервере (Beget)

Основной сайт на Beget использует MySQL и постоянные изображения; резервная площадка Vercel продолжает использовать Supabase. Смена переменной **не переносит данные**. Ответы и результаты тестов по-прежнему не сохраняются; готовность к обработке персональных данных нужно оценивать отдельно.

1. Создайте отдельную MySQL/MariaDB-базу в кабинете хостинга. Нужны InnoDB, `utf8mb4`, права на создание четырёх таблиц, чтение и запись. Доступ к БД ограничьте сервером приложения.
2. На тестовом сервере задайте `DATA_PROVIDER=mysql`, `MYSQL_HOST`, `MYSQL_PORT`, `MYSQL_USER`, `MYSQL_PASSWORD`, `MYSQL_DATABASE`. Значения берите из панели хостинга, не из примеров. Для удалённого подключения через недоверенную сеть настройте проверяемый TLS (`MYSQL_SSL_CA`); отключать проверку сертификата нельзя.
3. Создайте постоянный каталог вне `public`/`public_html`, например `/home/m/ACCOUNT/SITE/private-media`, и задайте его абсолютный путь в `MEDIA_ROOT`. На Beget каталог должен находиться **внутри каталога сайта, но вне `public_html`**: веб-процесс сайта работает под отдельным пользователем и не имеет доступа к произвольным каталогам аккаунта. Проверьте права этого пользователя на чтение и запись после переноса/восстановления; не используйте `chmod 777`. Этот каталог не удаляется при обновлении приложения. В Vercel файловая система не подходит для такого режима.
4. Скопируйте `.env.example` в `.env.local` и заполните серверные параметры; не публикуйте файл. Для разового переноса также нужны URL и сервисный ключ исходного Supabase.
5. Подготовьте таблицы и перенесите данные:

```bash
npm run mysql:init
# Остановите изменения в обеих админках на время переноса.
npm run mysql:import
```

`mysql:init` применяет `scripts/mysql/schema.sql`, не удаляя существующие таблицы. Импорт **не меняет Supabase**: переносит четыре таблицы и файлы Storage, проверяет количество строк, содержимое и SHA-256 файлов, заменяет ссылки на изображения в JSON и Markdown/HTML на `/media/...`. Имена с Unicode преобразуются в переносимые ASCII-имена. Неизображения сохраняются для резервирования, но не публикуются через маршрут изображений. Приватные бакеты сохраняются в закрытом префиксе `_private/`; ссылки на такие объекты в контенте останавливают импорт, а не делают файл публичным. При изменении исходных данных или видимости бакетов во время переноса операция прерывается. На непустой базе импорт остановится; для осознанной замены нужны `--force --pre-backup <новый-каталог>`.

После переноса перезапустите Node/Passenger: кэш мог содержать данные до импорта. Проверьте главную, цены, тесты, админку и загрузку фото на тестовом домене. Только после этого переключайте основной домен. До настройки HTTPS не входите в удалённую админку и не ослабляйте Secure-cookie. Резервный Vercel-деплой остаётся на Supabase; его ключи и workflows не удаляйте.

### Тестовый стенд с демонстрационными данными

Используйте отдельную пустую базу и отдельный постоянный каталог изображений. Задайте `DATA_PROVIDER=mysql`, `SITE_PREVIEW=1`, параметры тестовой базы и её `MEDIA_ROOT`, затем:

```bash
npm run mysql:init
npm run mysql:demo -- --confirm TEST_DATABASE_NAME
npm run build
```

Команда создаёт две демонстрационные услуги, два коротких теста и изображения-заглушки. Supabase не запрашивается, настоящие контакты заменяются ссылками на раздел тестов. Непустая база или каталог изображений приводят к отказу без перезаписи; имя подтверждения должно совпадать с `MYSQL_DATABASE`. Файлы из `supabase/seed/` используются только этой разовой командой, не во время работы сайта.

На тестовом HTTP-деплое Beget обработчик Passenger дополнительно закрывает `/admin` и `/api/admin/*`, выставляет `X-Robots-Tag: noindex, nofollow, noarchive` и запрещает обход через `robots.txt`. Это конфигурация тестового сервера, а не ослабление защиты приложения. `SITE_PREVIEW=1` сам по себе **не закрывает админку** и не заменяет HTTPS. Не вводите персональные данные в тестовом стенде.

### Резервирование MySQL

MySQL и постоянные изображения резервируются ежедневно через `mysql-backup.yml`;
процедура описана ниже в разделе «Резервные копии MySQL на Beget». Копии Supabase
отдельны и не заменяют эти снимки. Команды для ручной работы:

```bash
# Каждый снимок — в новый, ещё не существующий каталог.
npm run mysql:backup -- --output backups/snapshot-2026-10-15
# В пустую подготовленную базу; подтверждение должно точно совпасть с MYSQL_DATABASE.
npm run mysql:restore -- --input backups/snapshot-2026-10-15 --confirm DATABASE_NAME
# Замена непустой базы требует предварительного снимка.
npm run mysql:restore -- --input backups/snapshot-2026-10-15 --confirm DATABASE_NAME --force --pre-backup backups/before-restore
```

Снимок содержит четыре таблицы, весь `MEDIA_ROOT` и манифест целостности. Перед резервированием/восстановлением остановите изменения в приложении; для восстановления лучше полностью остановить Node/Passenger. После восстановления перезапустите приложение для очистки кэша. Скрипт проверяет данные и откатывает транзакцию при ошибках, но SQL и файловая система не образуют единую crash-atomic транзакцию: после аварийного отключения процесса может потребоваться восстановление из предварительного снимка.

**Снимки не зашифрованы.** Храните их вне web root, не коммитьте, ограничьте права и шифруйте перед отправкой на внешнее хранилище. Эти команды покрывают текущие четыре таблицы сайта, а не произвольные будущие таблицы. Периодически проверяйте восстановление в отдельной базе.

Проверки хранилищ: `npm run test:mysql`. Для интеграционного сценария задайте отдельную пустую базу с именем, заканчивающимся на `_test`, примените `mysql:init`, передайте её имя через `MYSQL_TEST_DATABASE`, а подключение — через `MYSQL_*`. Интеграционный сценарий очищает данные **только этой тестовой базы**; без `MYSQL_TEST_DATABASE` он пропускается.

Отдельный CLI-сценарий (`scripts/mysql-integration.test.mjs`) включается через `MYSQL_INTEGRATION=1` и использует пустую локальную базу `MYSQL_DATABASE` с суффиксом `_test`: проверяет импорт с тестовым HTTP-источником, бэкап, восстановление и откат ошибки внешнего ключа. Если одновременно включены оба сценария, `MYSQL_DATABASE` и `MYSQL_TEST_DATABASE` должны обозначать **разные** тестовые базы.

## Публикация

### Основной сайт на Beget: автодеплой из main

Основной домен обслуживает Beget, режим данных — MySQL. После push/слияния в
`main` workflow `PR checks` сначала выполняет lint, проверку типов, сборку и
регрессионные тесты. Только после их успеха job `Deploy to Beget` передаёт исходники
этого коммита по SSH. Для pull request публикация отключена. Ручной повтор:
Actions → PR checks → Run workflow → ветка `main`.
Синхронизация запасного фото после собственного коммита в `main` явно запускает
этот же workflow: push с `GITHUB_TOKEN` сам по себе не запускает другие Actions.

На сервере `scripts/beget/gateway.sh` принимает только `deploy <полный SHA>`,
блокирует параллельные операции, проверяет архив и создаёт отдельный каталог
`releases/<SHA>-<суффикс>`. Зависимости устанавливаются через `npm ci`, сборка идёт
на Beget с одним worker (`BEGET_BUILD=1`). Текущий сайт продолжает работать.
Затем проверяются главная, тесты, фото, MySQL-контент, индексация и защита админки
на loopback. Passenger переключается атомарной заменой `.htaccess`; те же проверки
повторяются по HTTPS с проверкой сертификата и SHA релиза. При ошибке после
переключения восстанавливается предыдущий `.htaccess`, Actions показывает ошибку.
Сбой до переключения не меняет работающий сайт.

Сохраняются текущий и предыдущий управляемые релизы, а также статические файлы
предыдущей сборки для открытых вкладок. Старые приложения, созданные до автодеплоя,
не удаляются. БД и постоянный `MEDIA_ROOT` не входят в релиз: автодеплой не выполняет
импорт, восстановление, seed или миграции схемы. Изменения схемы требуют отдельной
совместимой процедуры. Изображения из кэша Next переносятся в новый релиз.

Разовая установка администратором: в каталоге сайта создайте `deploy/`, установите
туда `gateway.sh` и `export-backup.sh` из `scripts/beget/` с окончаниями строк LF, скопируйте рабочий
`.env.local` в `deploy/runtime.env`, совместимый бинарник Node 24 — в `deploy/node`.
`deploy/config.json` содержит `{"origin":"https://ekaterinazhuk.ru","address":"45.130.41.213"}`.
Эти файлы находятся вне `public_html`; сохраните ограничения доступа и наследуемые
ACL веб-пользователя Beget. Секреты БД остаются на сервере; не отправляйте
`runtime.env` в GitHub или архив исходников. После изменения настроек обновляйте
`deploy/runtime.env`: следующий релиз возьмёт его новую копию.

Для GitHub Actions нужен отдельный SSH-ключ с записью
`restrict,command="/bin/bash /ABSOLUTE/SITE/deploy/gateway.sh"` в `authorized_keys`.
Ограничение убирает интерактивный shell и туннели, но **не изолирует код деплоя**:
сборка доверенного `main` выполняется от имени аккаунта хостинга. Ограничьте доступ
к `main` и настройкам Actions. Изменения самого gateway устанавливаются отдельно
администратором; остальные скрипты деплоя приходят с каждым коммитом.

| Настройка GitHub | Имя | Значение |
|---|---|---|
| Secret | `BEGET_DEPLOY_SSH_KEY` | закрытый ключ только для деплоя |
| Secret | `BEGET_DEPLOY_KNOWN_HOSTS` | заранее проверенный ключ SSH-сервера |
| Variable | `BEGET_DEPLOY_SSH_HOST` | SSH-хост Beget |
| Variable | `BEGET_DEPLOY_SSH_USER` | SSH-пользователь Beget |

Ключ резервного копирования остаётся отдельным; его forced command указывает на
`deploy/export-backup.sh`. Обёртка определяет активный релиз по `.htaccess` и держит
общую блокировку с деплоем, поэтому бэкапы не привязаны к устаревшему приложению.
Для ручного отката администратор с полным SSH-доступом под блокировкой
`deploy/deploy.lock` заменяет `public_html/.htaccess` сохранённым
`deploy/previous.htaccess` через временный файл и `mv` на том же диске. Проверьте
HTTPS и `/__hosting-health`; endpoint возвращает SHA работающего релиза, без секретов.
`deploy/state.json` хранит пути текущего и предыдущего успешного релиза.

### Контроль SEO и скорости

Первый экран предзагружает только Mulish Regular и SemiBold; остальные начертания
и шрифт цен Play загружаются по необходимости. Оба набора Mulish используют одну
явно заданную семью, поэтому жирный текст и курсив не заменяются искусственными
начертаниями. Фото профиля загружается с `loading="eager"` и `fetchPriority="high"`;
`sizes` учитывает отступы страницы на телефоне и планшете. Качество фото, оформление
и скелетон при этом не меняются. После `npm run build` выполните
`node --test scripts/tests/first-screen-build.test.mjs`: проверка контролирует два
предзагружаемых файла и наличие всех начертаний Mulish в собранном CSS.

HTML публичных страниц остаётся динамическим, с `no-store`; данные кэшируются
отдельно и сбрасываются при сохранениях. На Beget при замере 16.10.2026 тёплый
рендер главной на loopback занимал около 14 мс по медиане, тогда как внешнее
соединение добавляло существенно больше. Отдельный кэш HTML не добавлялся:
при таком соотношении он даёт небольшой выигрыш и требует дополнительного
согласования с инвалидацией данных. Админка и авторизованные ответы не должны
попадать в общий кэш. Замеры повторяйте после смены хостинга или заметного роста
нагрузки; это локальный эксперимент, а не оценка полевых Core Web Vitals.

После настройки домена проверьте: `https://ekaterinazhuk.ru/` отвечает 200, `https://www.ekaterinazhuk.ru/` перенаправляет на него с сохранением пути и query-параметров. То же направление должно соблюдаться при переходе с HTTP.

В Google Search Console добавьте доменный ресурс `ekaterinazhuk.ru`, подтвердите владение DNS-записью из интерфейса сервиса и отправьте `https://ekaterinazhuk.ru/sitemap.xml`. В Яндекс Вебмастере добавьте `https://ekaterinazhuk.ru`, подтвердите владение и отправьте тот же sitemap. Не добавляйте страницы тестов в sitemap до их публичного запуска со ссылкой с главной; админка не индексируется постоянно.

Скорость проверяйте в PageSpeed Insights для главной, списка тестов и отдельного теста, отдельно на мобильном и десктопе. Лабораторные Lighthouse-замеры сравнивайте при одинаковых условиях; полевые LCP, INP и CLS оценивайте по данным реальных пользователей, если их достаточно. Отсутствие полевых данных не означает хорошую или плохую скорость.

## GitHub Actions

Для совместимости с плагинами `eslint-config-next` используется ESLint 9: текущие `eslint-plugin-import`, `eslint-plugin-react` и `eslint-plugin-jsx-a11y` ещё не объявляют поддержку ESLint 10. ESLint 9 уже помечен устаревшим; переход на 10 следует выполнить после обновления совместимости плагинов. В npm, поддерживающем `allowScripts`, разрешён установочный скрипт конкретной версии `unrs-resolver`, используемого резолвером TypeScript.

Известное предупреждение `npm audit`: `braces` через `micromatch` → `fast-glob` → `@next/eslint-plugin-next` (зависимости разработки). На момент проверки исправленная версия `braces` не опубликована; `npm audit fix --force` предлагает несовместимый откат `eslint-config-next` до 14, поэтому применять его нельзя. Проверка `npm audit --omit=dev` не обнаруживает уязвимостей в production-зависимостях.

`npm run lint` не допускает ни ошибок, ни предупреждений (`--max-warnings=0`); любое новое предупреждение блокирует проверку PR. Перед проверкой TypeScript workflow запускает `npx next typegen`, чтобы в чистом checkout были доступны типы маршрутов и изображений Next.js.

- **`pr-checks.yml`** — проверяет каждый PR в `main`, изменения в `main` и ручные запуски: `npm ci`, ESLint, TypeScript, production-сборку и регрессионные тесты. Проверки используют Node.js 24 без секретов и рабочей базы. Только для `main` после их успеха отдельный job публикует релиз на Beget с ключом деплоя. Повторный запуск для того же PR отменяет предыдущую проверку; работающий деплой `main` не отменяется новым коммитом.

Чтобы проверка блокировала мердж при ошибке, после первого запуска добавьте **Lint, types and build** в обязательные status checks правила защиты `main` (Settings → Rules → Rulesets). Сам workflow не запрещает мердж без настройки этого правила.

Адрес сайта в обоих workflow берётся из переменной репозитория `SITE_URL` (Settings -> Secrets and variables -> Actions -> Variables), по умолчанию `https://ekaterinazhuk.ru`. Запускать можно вручную из вкладки Actions. GitHub отключает cron-workflow в репозиториях без коммитов более 60 дней - тогда включите их заново.

- **`supabase-keepalive.yml`** — раз в 3 дня запрашивает `/api/content` и `/api/tariffs` выбранного сайта. Основной домен теперь читает MySQL, поэтому эти запросы не поддерживают активность Supabase. К Supabase отдельно обращается ежедневный `supabase-backup.yml`; Free-план может приостанавливать проект при отсутствии активности.
- **`sync-fallback-photo.yml`** - раз в неделю (понедельник) скачивает текущее фото профиля из Supabase и, если оно изменилось, коммитит его в `public/photo.webp` и `src/assets/images/photo.webp`. Это запасное фото для SEO/OG и страницы, когда в Supabase фото нет. Если на `main` включена защита веток, разрешите боту `github-actions` пушить в неё.
- **`supabase-backup.yml`** - раз в сутки (03:00 UTC) выгружает **все таблицы схемы `public` и все файлы Storage** и сравнивает отпечаток данных с последним сохранённым бэкапом. Если ничего не изменилось, запуск просто завершается и новый архив не создаётся. Если данные изменились, архив шифруется и сохраняется как артефакт запуска на 90 дней. Принудительный бэкап: Run workflow -> галочка `force`. Скрипт сам находит таблицы и колонки, поэтому при изменении структуры данных ничего править не нужно. Архив шифруется, потому что репозиторий публичный.

### Резервные копии MySQL на Beget

`mysql-backup.yml` ежедневно в 03:30 UTC и по ручному запуску получает четыре таблицы
и все файлы `MEDIA_ROOT` по SSH, шифрует архив AES-256 и сохраняет его в GitHub
Actions на 90 дней. Каждый запуск создаёт новую копию, даже если данные не менялись:
так последняя копия не исчезнет из-за срока хранения. После шифрования workflow
расшифровывает архив во временном каталоге и проверяет SHA-256 таблиц и изображений;
это проверка целостности, а не полноценная проверка восстановления в MySQL.
В GitHub загружается только `backup.tar.gz.gpg`, без `.env.local`, SSH-ключа и
незашифрованных данных. Временные файлы удаляются после запуска, ошибки видны
в Actions. Пароль шифрования тот же `BACKUP_PASSPHRASE`, что у копий Supabase;
храните его также отдельно от GitHub.

На Beget установите `scripts/beget/export-backup.sh` в постоянный каталог
`SITE/deploy`, а `scripts/export-mysql-backup.sh` оставьте в каждом релизе.
Для GitHub создайте **отдельную** пару SSH-ключей, у которой публичный
ключ в `~/.ssh/authorized_keys` имеет ограничения:

```text
restrict,command="/bin/bash /ABSOLUTE/SITE/deploy/export-backup.sh" ssh-ed25519 PUBLIC_KEY github-mysql-backup
```

Этот ключ не даёт интерактивную оболочку, туннели, загрузку произвольных файлов или
выбор команды: сервер принимает только `export-mysql-backup`, определяет активное
приложение по `.htaccess` и выполняет экспорт под общей блокировкой с деплоем.
Снимок временно создаётся
в соседнем с приложением `private-backups`, вне `public_html`, и удаляется после
передачи; параллельные экспорты исключены `flock`. На сервере нужны Bash, `flock`,
`tar`, Node.js 24 и установленные зависимости приложения.

В GitHub → Settings → Secrets and variables → Actions задайте:

| Тип | Имя | Значение |
|---|---|---|
| Secret | `MYSQL_BACKUP_SSH_KEY` | приватный ключ только для экспорта |
| Secret | `MYSQL_BACKUP_KNOWN_HOSTS` | строка `known_hosts` с ключом сервера, проверенным через панель Beget; не слепой `ssh-keyscan` |
| Secret | `BACKUP_PASSPHRASE` | длинный пароль шифрования, сохранённый также отдельно |
| Variable | `MYSQL_BACKUP_SSH_HOST` | SSH-хост из панели Beget |
| Variable | `MYSQL_BACKUP_SSH_USER` | пользователь хостинга |

Первый запуск выполните вручную через Actions → **MySQL backup**. Расписание
действует только после попадания workflow в основную ветку. Следите за ошибками и
уведомлениями Actions; в публичном репозитории расписание может отключиться после
60 дней без активности.

Скачайте артефакт нужного запуска и расшифруйте его, вводя пароль по запросу GPG:

```bash
gpg --output backup.tar.gz --decrypt backup.tar.gz.gpg
mkdir snapshot
tar -xzf backup.tar.gz -C snapshot
# В отдельном тестовом окружении с пустыми MySQL и MEDIA_ROOT:
npm run mysql:init
npm run mysql:restore -- --input snapshot --confirm TEST_DATABASE_NAME
```

Перед восстановлением остановите изменения в приложении; на непустом назначении
нужны `--force --pre-backup <новый-каталог>`. Перезапустите приложение после
восстановления. Автоматическая копия не заменяет пробное восстановление в отдельную
базу. Для плановой копии выбирайте время без правок в админке: экспорт использует
транзакционный снимок таблиц и проверяет неизменность файлов, но MySQL и файловая
система не образуют общую транзакцию.

Эта схема предназначена для текущего контента сайта без персональных данных
посетителей. До добавления таких данных пересмотрите состав копий, место хранения,
сроки и правила доступа; шифрование само по себе не решает вопросы локализации и
трансграничной передачи.

### Резервные копии Supabase

На бесплатном плане Supabase нет собственных бэкапов, поэтому используется этот workflow.

**Настройка (один раз)**

1. Settings -> Secrets and variables -> Actions -> **Secrets** -> New repository secret. Добавьте:
   - `SUPABASE_URL` - адрес проекта (то же, что `NEXT_PUBLIC_SUPABASE_URL`);
   - `SUPABASE_SERVICE_ROLE_KEY` - сервисный ключ (Supabase -> Project Settings -> API);
   - `BACKUP_PASSPHRASE` - придуманный длинный пароль для шифрования. **Сохраните его отдельно** (менеджер паролей): без него архив не открыть.
2. Вкладка Actions -> **Supabase backup** -> Run workflow, чтобы проверить, что всё работает.

**Как скачать копию**

1. Actions -> Supabase backup -> запуск, у которого есть раздел Artifacts (в запусках без изменений его нет) -> `supabase-backup-…` (файл `backup.tar.gz.gpg`).
2. Расшифровать и распаковать:

```bash
gpg --batch --pinentry-mode loopback --passphrase "ВАШ_ПАРОЛЬ" -o backup.tar.gz -d backup.tar.gz.gpg
tar -xzf backup.tar.gz
```

Получится папка `backup/`: `tables/*.json` (по файлу на таблицу), `storage/<бакет>/…` (файлы, например фото), `schema.openapi.json` (описание структуры) и `manifest.json` (количество строк и файлов).

**Как восстановить**

*Простой способ (из браузера, без консоли):*

1. GitHub -> Actions -> **Supabase restore** -> Run workflow.
2. `run_id` - число из адреса нужного запуска Supabase backup (`…/actions/runs/<число>`); оставьте пустым, чтобы взять самый свежий бэкап.
3. В поле `confirm` введите `RESTORE` и запустите.

Workflow сам скачает и расшифрует архив (секреты те же), перед восстановлением сохранит снимок текущих данных как артефакт `pre-restore-…` (на случай, если нужно откатиться) и запишет данные в Supabase. Проект, в который идёт восстановление, определяют секреты `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY`. После восстановления изменения на сайте появятся не позже чем через час (кэш) или сразу после любого сохранения в админке.

Восстановление **добавляет и обновляет** строки и файлы из бэкапа, но **не удаляет** то, что появилось после бэкапа.

*Вручную (например, в новый проект Supabase):*

1. В пустом или новом проекте Supabase создайте структуру таблиц (SQL из раздела «Настройка Supabase»).
2. Запустите восстановление (нужны `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` нового проекта, например из `.env.local`):

```bash
node --env-file=.env.local scripts/restore-supabase.mjs backup
```

Скрипт записывает строки по первичному ключу (существующие обновляются, недостающие добавляются) в порядке внешних ключей, создаёт бакеты и загружает файлы. Локально такую же копию можно сделать командой `node --env-file=.env.local scripts/backup-supabase.mjs backup` (папку `backup/` не коммитьте: в ней данные сайта).

Если в схеме появилась **новая таблица**, она попадёт в бэкап автоматически, но структуру (SQL) нужно хранить в репозитории отдельно: бэкап сохраняет данные, а не `CREATE TABLE`.

## Формат данных

> Если сайт сломался после изменений, проверьте, не потерялась ли где-то скобка, кавычка или запятая.

Начальные значения лежат в [supabase/seed](supabase/seed) (изменение этих файлов влияет на сайт только после `npm run seed -- --force`).

### Общий контент (`content_json`)

У каждого значения есть свой ключ, например `"fullName": "Екатерина Жук"`. Любое значение можно менять; новые типы значений требуют изменений в коде (`src/lib/contentTypes.ts`).

> Удалять значения (за исключением элементов списков) нельзя!

Пример структуры элемента прайса (актуальный прайс на сайте берётся из таблиц `tariffs`):

```json
  "descriptionPath": "/pricelist/имя_файла_с_описанием.md",
  "packages": [
    {
      "name": "1 встреча",
      "price": { "regular": { "amount": 3333, "currency": "₽" } }
    },
    {
      "name": "4 встречи",
      "price": {
        "regular": { "amount": 9999, "currency": "₽" },
        "discounted": { "amount": 8888, "currency": "₽" }
      }
    }
  ],
  "title": "Название продукта"
}
```

Комментарии в JSON недопустимы. `discounted` опционален, пакетов должно быть минимум один.
